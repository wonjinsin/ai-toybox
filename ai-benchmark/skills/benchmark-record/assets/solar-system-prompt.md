Task version: `solar-system-observatory-2`.

Create an HTML-based interactive 3D solar system observation tool using Three.js.

Requirements:

1. Display one sun and exactly three planets in a genuine Three.js-rendered 3D scene. Use 3D geometry and a camera whose orbit changes the view of that geometry, not a flat drawing that only imitates depth.
2. Start the planets orbiting the sun automatically at simulation time 0 and global speed 1x when the scene opens, including after reload. Start in the full-system overview with no selected planet.
3. Give the three planets different sizes, colors, and orbital speeds. Use circular orbits with periods of 12, 24, and 48 simulation seconds. These are benchmark values, not real astronomical periods. Keep each planet's initial orbital phase fixed across playback, seeking, and reloads so that a given simulation time always produces the same orbital positions.
4. Provide a pause/resume button. Pausing must freeze simulation time and all planet orbital positions. Resuming must continue from the current simulation time without a position jump. Planet selection and camera controls must remain usable while paused.
5. Provide a global speed control ranging from 0.25x to 4x that changes the rate of simulation time while preserving the planets' relative orbital speeds. Changing speed must not change the current simulation time or orbital positions. A speed change while paused must take effect when playback resumes.
6. Make `output/index.html` run when opened directly in a browser as a `file://` page, without starting a server or running a build step to view it. Use `file://`-compatible scripts and assets; do not rely on local ES module scripts/imports or `fetch()` or XHR for local files.
7. Allow users to select any planet either by clicking it in the 3D scene or by choosing it from a labeled planet list. Both methods must update the same selection, visibly highlight the selected planet, and update an information panel showing its name, orbital period in simulation seconds, and current orbital angle in degrees. The angle must agree with the rendered orbital position and update during playback and seeking. With no selection, show no planet highlight and an explicit no-selection information state.
8. Provide a tracking mode for the selected planet and a control to return to the full-system overview. While tracking, keep the selected planet near the center of the view as it moves. Selecting another planet while tracking must update the highlight, information panel, and camera target together. Returning to the overview must preserve the selected planet, simulation time, global speed, and playback state. Tracking requires a selected planet. With no selection, disable or visibly reject tracking without changing state.
9. Provide a time slider for seeking within 0 to 120 simulation seconds and a visible current-time readout. Seeking must pause playback and immediately update all planet positions, the selected planet's information, and the tracking camera when active. Playback must stop at 120 seconds; it must not wrap or continue beyond the range. Seeking to an earlier time must allow playback to resume from that time.
10. Allow camera orbit and zoom around the current target in both overview and tracking modes, including while paused. A camera drag must not be interpreted as a planet-selection click. Interacting with the planet list, time slider, speed control, or buttons must not trigger scene selection or camera movement.
11. At viewport sizes of 1440x900 and 390x844 CSS pixels, keep the scene and all primary controls usable without horizontal scrolling. Information panels must not cover or block the controls needed for selection, tracking, seeking, speed changes, pause/resume, snapshots, or JSON import/export. Vertical scrolling is allowed.
12. Provide an observation snapshot list with capture, restore, and delete controls. Keep at most three snapshots. Each snapshot has a unique, stable, nonempty string ID and captures one instant's simulation time, global speed, selected planet or no selection, view mode, and the orbital angles of all three planets. Append captures to the list and preserve the remaining order on deletion. Show the captured values in the list or an inspectable snapshot detail panel, including all three angles in degrees. Captured values must remain unchanged when live playback, speed, selection, view, or time changes. Derive snapshot angles from captured time and the fixed phases in requirement 3, never from current live time. Capture and deletion must not change live state. A fourth capture must show a visible capacity message without replacing any snapshot. Deleting one snapshot must allow another capture. Restore must set the captured time, speed, selection, and view mode together, pause playback, and immediately synchronize all planet positions, the highlight, information, and camera target. Restoring no selection must clear any previous highlight and selected-planet information. Use the same deterministic standard full-system framing for overview restores and a deterministic standard selected-planet framing for tracking restores. Playback state and user camera orbit/zoom offsets are not part of a snapshot and are not restored. Restoring the same snapshot after different live interactions must produce the same observable state and framing at the same viewport size.
13. Provide a labeled textarea and explicit export and import controls for the snapshot JSON contract below. Export the entire current snapshot list to the textarea without changing the list or live state. Import must validate the whole input before changing anything. A valid import replaces only the snapshot list, preserving live time, speed, selection, playback state, view mode, and camera framing. An invalid import must show a visible error and leave both the existing list and live state unchanged. Neither operation may depend on an OS file picker. Normal playback may continue during these operations, but import/export must not seek, pause, resume, or otherwise alter it.
14. Persist the snapshot list after every successful capture, deletion, or import. Reloading the same page in the same browser storage context must recover the list with the same IDs, order, values, and derived angles, while the live scene starts from requirement 2 rather than restoring a snapshot automatically. Apply the same JSON validation rules to saved data. Invalid saved data must yield an empty snapshot list, a visible recovery notice, and usable live controls. If storage is unavailable or a write fails, keep the in-memory tool usable and visibly report that saving is unavailable. Do not claim that unsaved data will survive reload.
15. Make every primary DOM control usable with the keyboard, including pause/resume, speed, time, planet selection, tracking/overview, snapshot capture/restore/delete, the textarea, and import/export. Provide meaningful accessible names, visible keyboard focus, and no keyboard trap. Use normal keyboard operation for each control, including Tab navigation and Enter, Space, or arrow keys as appropriate. Camera orbit/zoom and clicking planets on the canvas need not be keyboard-operated because the planet list provides keyboard selection.

Snapshot JSON contract:

- The root must be a JSON object, not an array or `null`, with both required fields `version` and `snapshots`.
- `version` must be the JSON number `1`, not the string `"1"`. Reject every other version.
- `snapshots` must be an array of zero to three snapshot objects. Preserve array order on import, display, persistence, and export. An empty array is valid and clears the list on import without changing live state.
- Every snapshot must be a JSON object, not an array or `null`, with all five required fields `id`, `time`, `speed`, `selectedPlanet`, and `viewMode`. Missing fields are invalid, even where `null` is an allowed value.
- `id` must be a string of length at least one. IDs must be unique within the list by exact, case-sensitive string equality. Do not coerce, trim, or regenerate imported IDs. Captured IDs must remain stable through restore, export, import, and reload and must not collide with IDs already in the list.
- `time` must be a finite JSON number in the inclusive range 0 to 120 simulation seconds. Fractions are allowed.
- `speed` must be a finite JSON number in the inclusive range 0.25 to 4. Fractions are allowed, including values between any presets offered by the UI.
- `selectedPlanet` must be either JSON `null` for no selection or one of the three planet IDs. Choose three distinct, nonempty, case-sensitive string IDs once for the implementation. Keep the name/ID mapping stable across reloads. Show that mapping beside the planet names or JSON controls so users can construct valid input. Export the actual ID, not a display name or array index, when that planet is selected. Reject unknown IDs, numeric indices, empty strings, and the string `"null"`.
- `viewMode` must be exactly the string `"overview"` or `"tracking"`. `"overview"` permits either a selected planet or `null`. `"tracking"` requires a non-null valid `selectedPlanet`.
- Reject malformed JSON, wrong types including numeric strings and booleans, non-finite numbers, missing fields, duplicate IDs, out-of-range values, invalid planet references, and tracking without a selection. Do not clamp values or import a valid prefix of an invalid list.
- Ignore extra object keys during import and saved-data validation. Export only the required root and snapshot fields. Angles are derived from `time` and fixed phases, not authoritative imported state. Camera offsets and playback state are not serialized.
- Use the same versioned object for persistence. No particular storage key or serialization whitespace is required.

For example, an empty exported list is exactly this object apart from whitespace:

```json
{"version":1,"snapshots":[]}
```

Acceptance scenario:

1. Open the scene and confirm that all three planets orbit automatically.
2. Select a planet in the scene and enable tracking. Confirm that its highlight, live information, and camera target agree.
3. Pause, then seek to simulation time 30 seconds. Confirm that all planets move to their positions for that time and that the selected planet's information and tracking camera update while playback stays paused.
4. Set the global speed to 2x while paused. Confirm that time and orbital positions remain unchanged.
5. Resume. Confirm that motion continues from the sought positions without a jump and simulation time advances at twice the real-time rate.
6. Select a different planet from the list while tracking. Confirm that the selection, information panel, and camera target switch together without changing time, speed, or playback state.
7. Return to the overview. Confirm that the full system is visible and selection, time, speed, and playback state are preserved.
8. Pause and seek to 30 seconds again. Confirm that all orbital positions match the earlier 30-second state, regardless of the intervening speed and selection changes.

Confirm meaningful control names and visible focus, no focus trap, no accidental canvas selection or movement, and no horizontally hidden primary controls.

The intended experience is an observation tool with clear controls and consistent state across selection, camera tracking, time seeking, playback, and saved observations. Keep the visual design and implementation approach open while satisfying the specified behavior.
